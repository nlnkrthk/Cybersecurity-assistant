The description is not generated by an LLM. flow_to_text builds it from a fixed template for each sampled row. It starts with Traffic label: BENIGN. for benign rows or Attack: <label>. for other labels. It then adds available protocol and port values, followed by available flow measurements and flags. Numeric values are formatted compactly, and units are added where applicable—for example, flow duration in microseconds and byte measurements in bytes.

Missing or NaN values are omitted, not replaced with N/A or zero. Protocol numbers 1, 6, and 17 are displayed as ICMP, TCP, and UDP respectively; other values are shown as numbers. Source/destination IP and timestamp are kept in the Parquet but aren’t included in incident_text.

For example: Attack: PortScan. Destination port: 80. Flow duration: 75 microseconds. Forward packets: 1. Backward packets: 0. SYN flags: 1.

build_search_indexes.py takes the prepared Parquet dataset and builds two indexes from it: a BM25 keyword index and a Chroma vector index. It does not reload the raw CSVs or generate new incident descriptions.

Flow from start to finish
Set up paths and offline mode
The script disables Hugging Face network access and Chroma telemetry, then sets the index locations:

BM25 cache: data/processed/bm25_index.pkl
Chroma database: data/processed/chroma
Load and validate Parquet
It reads incidents_100k.parquet into a Pandas DataFrame and checks required fields: incident_id, label, incident_text, and dst_port. It also checks that IDs are present and unique, labels and descriptions are present, and destination ports are numeric when populated.
See build_search_indexes.py and metadata.py.

Prepare aligned inputs
It indexes incident_text by incident_id and builds one metadata record per row. Metadata includes the ID and label, plus available connection details such as destination port, protocol, source port, IPs, and timestamp. Missing optional values are omitted rather than replaced with zero.
See metadata.py.

Create vector embeddings
The configured Sentence Transformer model—all-MiniLM-L6-v2—encodes every incident description in batches of 128. The script checks that there is one embedding per incident and logs the embedding dimensions (typically 384).
See embedder.py and build_search_indexes.py.

Build the BM25 keyword index
The same descriptions are normalized into tokens: case is folded, punctuation and separators are normalized, camel-case terms can be split, and common suffixes such as -ing, -ed, and plural -s are handled. BM25 uses those tokens to rank exact keyword matches. Negative IDF values are clamped to zero. The IDs, texts, and metadata are saved to a temporary pickle file first.
See bm25_index.py and build_search_indexes.py.

Build the Chroma vector index
Chroma stores each incident’s embedding alongside its ID, text, and metadata. It uses cosine distance and adds documents in batches of 5,000. When rebuilding, the existing Chroma collection is deleted and recreated.
See chroma_store.py.

Verify both indexes against the source rows
Before the temporary BM25 file replaces the saved cache, the script checks:

BM25 IDs match the Parquet row order.
Chroma has the expected document count and embedding dimension.
Chroma IDs, descriptions, and metadata match the Parquet records.
If checks pass, the temporary BM25 file replaces the saved one and the script reports success.
See build_search_indexes.py.

interactive_hybrid_search.py: end-to-end flow
The script is the terminal interface for searching the prepared Parquet data using BM25 keyword search, vector similarity, and a combined ranking called RRF. It loads existing indexes; it does not build or rebuild them.

1. Startup and imports
At startup, it attempts to configure Python’s SSL handling with truststore. If truststore isn’t installed or setup fails, it prints a warning and continues. It then adds the project’s src directory to Python’s import path and imports the data, index, and search components.

2. Read command-line options
The script accepts:

An optional query as a positional argument, for a one-time search.
--top-k N to control how many results to show from each method. The default is 5; values must be positive integers.
--debug to show token normalization and RRF score contributions.

3. Load and validate the incident data
It reads the prepared incidents_100k.parquet into Pandas. Before searching, it validates that the required retrieval columns are present and that incident IDs, labels, text, and destination ports meet the expected data requirements. It stops with an error if validation fails.

4. Find and load the cached indexes
The script expects both of these to exist:

data/processed/bm25_index.pkl
data/processed/chroma
If either is missing, it tells you to run build_search_indexes.py.

It then reads the incident descriptions and builds metadata from the Parquet rows. For BM25, it checks that the cached IDs, text, and metadata still match the current Parquet data. For Chroma, it checks that the stored IDs, text, and metadata align with those rows. If an index is stale or misaligned, the script exits and recommends rebuilding the indexes.

5. Load the query-embedding model
It loads the configured Sentence Transformer model, all-MiniLM-L6-v2. This model converts each search query into a vector so Chroma can find semantically similar incident descriptions. If model loading fails, the script reports an error and exits.

6. Run a query
HybridSearcher uses the same query in two ways:

BM25: Tokenizes the query and ranks descriptions containing matching terms. A higher BM25 score indicates a stronger keyword match.
Vector search: Embeds the query and searches Chroma for semantically similar descriptions. A lower vector distance indicates a closer match.
Both searches apply the same top-k setting. Exact duplicate descriptions are suppressed by default, so the results favor distinct text rather than multiple incidents with identical descriptions.

7. Combine rankings with RRF
The script combines the two ranked lists with Reciprocal Rank Fusion. With the default equal weights and k = 60, an incident appearing at rank r in a result list contributes:


A result appearing high in both lists gets contributions from both; a result found by only one method gets a contribution from that list alone. RRF uses ranks, not the raw BM25 scores or vector distances, so those differently scaled values are not compared directly.

8. Display results
For BM25, vector, and fused results, the script prints each incident’s:

Rank and incident ID
Label/type
Protocol and destination port
A preview of its incident_text
If an index returns an incident ID that does not exist in the validated Parquet data, the script raises an error instead of displaying mismatched details.

With --debug, it also prints the normalized query, BM25 tokens, and the BM25/vector rank and RRF contribution for each fused result.

9. Decide whether to exit or keep accepting queries
Query supplied on the command line: run it once, then exit.
No query, interactive terminal: repeatedly prompt for queries. Enter quit, exit, or q to stop.
No query, non-interactive input: run the built-in default query, DDoS attack high packet volume, once.
The main flow is in interactive_hybrid_search.py; the ranking and fusion logic is in HybridSearcher.search.
